# Архитектура системы MedMind AI Routing Module

## 1. Обзор

MedMind AI Routing Module - это B2B2C-сервис, который анализирует текстовые заключения лучевой диагностики и формирует персональный маршрут дальнейшего обращения пациента. Модуль встраивается поверх существующей МИС клиники и не заменяет ее.

Ключевое отличие: MedMind не генерирует DICOM-изображения и не парсит пиксели снимков. Модуль работает со структурированным текстом заключения (поля report и conclusion из DICOM SR) и добавляет patient-facing слой: понятный маршрут, бота/портал, Drip-реактивацию, Shared Care.

## 2. Компоненты системы

### 2.1. Backend (FastAPI + AI)

Технологии: Python 3.11, FastAPI, RuBERT-v2

Функции:
- Анализ медицинских заключений через AI-модель
- Определение срочности (red/yellow/green)
- Классификация типа исследования (маммография/КТ/рентген)
- Генерация персонального маршрута
- Формирование полей, совместимых с БФТ НПКЦ ДиТ ДЗМ

API Endpoints:
- POST /api/analyze - анализ заключения и формирование маршрута
- POST /api/drip-campaign - генерация сообщений для пациента
- GET /health - проверка статуса системы

### 2.2. Frontend МИС (React + TypeScript)

Технологии: React 18, TypeScript, Vite, @react-pdf/renderer

Функции:

- Генерация PDF-маршрута с конверсионными триггерами
- Создание QR-кода для пациента
- Управление Drip-campaign

### 2.3. Frontend пациента (PWA / patient.clinic.local)

Технологии: React 18, TypeScript, Vite

Функции:
- Персональное приветствие пациента

- Персональный план наблюдения на 3 месяца
- Вопросы к врачу от ИИ
- Shared Care (поделиться с родственником)

Развертывание:
- Локальный веб-портал в контуре клиники (patient.clinic.local)
- PWA для мобильных устройств
- Соответствие 152-ФЗ

### 2.4. Telegram Bot (MVP / Demo only)

Технологии: Python 3.11, Aiogram 3.x

Функции:

## 3. Поток данных

### 3.1. Основной сценарий (MVP через REST)

1. Врач загружает текстовое заключение в интерфейс MedMind
2. Backend вызывает model.predict_urgency(text) - возвращает urgency + confidence
3. Routing Engine маппит urgency - specialist, timeframe, red_flags
4. Генерируются next_steps (3-месячный план) и questions_for_doctor
5. Врач видит карточку пациента с таймером бронирования (2 часа)
6. Врач генерирует QR - пациент сканирует - попадает в бота/портал
7. Drip-движок отслеживает статус: если пациент не записался - Day 3 reminder - Day 7 эскалация администратору

### 3.2. Продакшн-сценарий (интеграция с ЕРИС ЕМИАС)

1. Рентген-аппарат - PACS - ИИ-сервис (например, "Третье мнение")
2. ИИ-сервис формирует DICOM SR + Kafka-Message в топик DICOMREPORTNOTIFY
3. MedMind Kafka Consumer читает сообщение, парсит поля:
   - pathologyFlag - маппится в urgency
   - confidenceLevel (0-100) - ai_confidence
   - report - сырое описание
   - conclusion - медицинское заключение
4. Далее - тот же Routing Engine + patient channel

## 4. Соответствие БФТ НПКЦ ДиТ ДЗМ

- Поле pathologyFlag (true/false) - urgency != "green" - pathology_flag: true
- Поле confidenceLevel (0-100) - ai_confidence × 100 - confidence_level
- Раздел "Описание" DICOM SR - Поле report в ответе API
- Раздел "Заключение" DICOM SR - Поле conclusion в ответе API
- Топик DICOMREPORTNOTIFY - REST-адаптер (MVP), готов к обертке в Kafka Producer за 1 день
- Шаблоны Приложения 11 - Тексты report/conclusion соответствуют структуре ММГ (11.2), РГ ОГК (11.4), КТ ОГК (11.1)
- Версионирование (SemVer) - modelVersion: "1.0.0" в Kafka-сообщении

## 6. Безопасность и 152-ФЗ

- On-Premise развертывание: все данные остаются в контуре клиники (patient.clinic.local)
- Telegram: используется только как MVP-канал; в продакшене заменяется на MAX/VK Teams или локальный PWA
- Персональные данные: не передаются внешним сервисам; PDF и QR содержат только ID пациента и ссылку на внутренний портал
- Медицинские ограничения: модель не является медицинским изделием, результаты носят информационный характер, требуется валидация врачом

## 7. Масштабирование

- Горизонтальное: Backend - stateless, легко масштабируется через Kubernetes
- Модель: загружается один раз при старте, shared между воркерами
- Kafka: consumer group позволяет параллельно обрабатывать несколько топиков
- Frontend: PWA с offline-режимом для пациентского портала
